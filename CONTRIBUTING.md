# Contributing to GeoTools

GeoTools is a Blender 5.2+ extension that bundles rusty-tiles and pyproj. Read
[docs/ROADMAP.md](docs/ROADMAP.md) first. It holds the plan and the decisions
behind it.

To learn what GeoTools does from a user's side, read the
[user guide](docs/guide/README.md). When you change what a user sees (a panel,
a button, an option or a workflow), update the guide page for that area too.

## Repository layout

| Path | What it holds |
|---|---|
| `geotools/` | The extension. Blender installs this directory. |
| `geotools/blender_manifest.toml` | The extension manifest. `platforms` and `wheels` are added at build time; do not add them here. |
| `geotools/core/` | Pure Python and numpy. Never imports `bpy`, so it can be tested with plain pytest. |
| `geotools/blender/` | The `bpy` glue: operators, panels and preferences. |
| `geotools/publish/` | The publish job (bpy-free): staging layout and lock, the worker thread that writes the GLB and runs rusty-tiles, the build record, and the preview helper. |
| `geotools/analysis/` | M5 analysis maths (bpy-free, like `core`): the sun (NREL SPA), sun hours and clear-sky insolation, the Moon (Meeus) and archaeoastronomy, points, distances and areas on Earth, 3D surface hydrology, and contours and sections. See [docs/design/m5-analysis.md](docs/design/m5-analysis.md). |
| `geotools/assets/` | `analysis_presets.blend`, the Geometry Nodes preset library, generated by `scripts/make_analysis_presets.py` (never edit it by hand; see [docs/analysis-presets.md](docs/analysis-presets.md)). |
| `geotools/bake/` | Empty, reserved for a later milestone. |
| `geotools/wheels/` | Fetched wheels (rusty-tiles, pyproj, certifi). Ignored by git, never committed. |
| `scripts/` | Wheel fetching, extension build, the Blender test runner and the sidebar screenshot tool. |
| `tests/core/` | pytest tests for `geotools/core`. They run without Blender. |
| `tests/blender/` | Tests that run inside Blender. |

`geotools/__init__.py` imports `bpy` only inside `register()` and
`unregister()`. Keep it that way. `tests/core/test_no_bpy.py` fails if
`geotools` or `geotools.core` imports `bpy` or the Blender glue.

## Performance rule

No Python loops over faces, vertices, loops or other mesh data. Use
`foreach_get` and `foreach_set` with numpy arrays, Geometry Nodes, or Cycles
bakes. Sources can have tens of millions of triangles, and a per-element Python
loop is far too slow at that size.

## File paths

GeoTools ships for Linux, macOS and Windows, and a project folder (the `.blend`
and its data) must open on any of them. Blender reads its own `//` paths with
either separator, but `bpy.path.abspath` keeps backslashes on Linux and macOS,
so every path GeoTools stores in its own properties goes through
`geotools/core/paths.py` (pure Python, tested with `ntpath` and `posixpath`
inputs on any OS) and its Blender glue `geotools/blender/blend_paths.py`:

- **Writing:** `blend_paths.portable(path)`. A path under the `.blend`'s
  folder is stored as `//sub/dir/file` with forward slashes; anything else
  (another folder, another drive, a UNC share, an unsaved `.blend`) stays
  absolute, as the OS spells it. A path property the user edits gets
  `update=blend_paths.portable_update("<attr>")`.
- **Reading:** `blend_paths.abspath(text)`, never `bpy.path.abspath`, for
  GeoTools' own properties and for image files GeoTools reads or checks
  (`blend_paths.image_path(image)`). `//` paths with `/` or `\` resolve
  against the `.blend`'s folder; absolute paths are used as they are. Nothing
  is searched for: a file that is not there is reported missing.
- **Comparing:** `paths.same_file(a, b)`, which compares resolved paths
  (macOS `/var` is `/private/var`; Windows temp folders can be 8.3 short names
  such as `RUNNER~1`). Never compare path text.
- **Saving elsewhere:** `blend_paths` re-expresses the stored `//` paths for
  the new folder on Save As (and makes paths under the folder relative on the
  first save); Save Copy leaves the open file's paths as they were. Loading a
  file never rewrites a path: older absolute or backslash paths are read as
  they are and stored portably the next time GeoTools sets them. A new path
  property must be listed in `blend_paths.stored_paths`.

Paths that only describe a build, such as `output` and `blend_file` in
`build.json`, are records of where it ran and are never resolved. Add-on
preferences (the rusty-tiles CLI, the Cesium folder) belong to one machine
and stay absolute.

## Development setup

You need Python 3.11 or later for the scripts. Blender 5.2 runs Python 3.13,
and ruff targets 3.13. You also need Blender 5.2 to build and to run the
Blender tests.

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install pytest numpy ruff pyproj==3.8.0   # pyproj at the pin in pyproject.toml
```

Without pyproj the reprojection tests (`tests/core/test_reproject.py`) are
skipped; everything else runs.

Lint and format:

```sh
ruff check .
ruff format --check .
```

## Fetching the wheels

The extension bundles three wheels, each pinned to one exact version under
`[tool.geotools.wheels]` in `pyproject.toml`:

| Pin | What for |
|---|---|
| `rusty-tiles` | Tiling, validation and placement (native, `cp310-abi3`). |
| `pyproj` | Reprojecting imported vector points (M8). PROJ and its `proj.db` are inside the wheel; no GDAL. Native, one wheel per CPython (`cp313-cp313`). |
| `certifi` | pyproj's only dependency (pure Python). |

The target platforms are `platforms` under `[tool.geotools]`.
`scripts/fetch_wheels.py` puts one wheel of every pin per platform in
`geotools/wheels/` (a pure `py3-none-any` wheel counts for every platform). It
empties that directory first, and checks each wheel's name, version and Python
tags against the pins and the target CPython.

Download every wheel for every platform:

```sh
python scripts/fetch_wheels.py
```

The rusty-tiles pin is 0.4.1, from PyPI. GeoTools needs 0.4.1's functions
(`supported_epsg_codes`, `resolve_source_crs`, `list_tiles`, `decode_tile`)
and reports an older wheel as not available.

This uses `pip download` from the running Python, or `uvx pip` if that Python
has no pip, so pip settings such as `PIP_INDEX_URL` apply.

`--from-dir` copies wheels from a local directory instead. `--from-dir DIR`
takes every pin from `DIR`; `--from-dir NAME=DIR` takes one pin from `DIR` and
downloads the others. To test an unreleased rusty-tiles, take it from a local
directory, for example a rusty-tiles `dist/` folder (`build_extension.py`
refuses a wheel whose version does not match the pin, so a release still
needs the pinned wheel):

```sh
python scripts/fetch_wheels.py --from-dir rusty-tiles=/path/to/rusty-tiles/dist --platform linux-x64
```

`--platform` takes any of `linux-x64`, `windows-x64` and `macos-arm64`. Repeat it or separate names with commas. Without it the script
fetches every platform in `pyproject.toml`.

A locally built Linux wheel is often tagged `linux_x86_64` rather than
`manylinux`. The script warns about this. Such a wheel is fine for local builds,
but do not ship it.

### A local Blender on another Python

Official Blender 5.2 runs CPython 3.13, and releases are built for exactly
that. Some Linux distributions build Blender against the system Python (Arch's
Blender 5.2.3 runs 3.14). rusty-tiles is `abi3` and loads in either, but pyproj
is not. Blender reads the Python versions from the wheel tags and refuses a zip
with `cp313` wheels on 3.14 ("This Python version (3.14) isn't compatible
with (3.13)"). For such a Blender, fetch and build for its Python:

```sh
python scripts/fetch_wheels.py --from-dir rusty-tiles=DIR --platform linux-x64 --python 3.14
python scripts/build_extension.py --python 3.14      # run_blender_tests.py passes this itself
```

Both scripts warn that the result is for local use only. A build without
`--python` refuses `cp314` wheels, so a release can't pick them up by mistake.

### How Blender picks wheels

When it installs or enables an extension, Blender
(`addons_core/bl_pkg/bl_extension_ops.py` and
`modules/_bpy_internal/extensions/wheel_manager.py` in 5.2):

1. Keeps the wheels for this system. The platform tag must be `any`, the
   exact platform, or the same architecture: `manylinux*_x86_64` on Linux,
   `macosx_*_arm64` (or `universal2`) on macOS. The glibc and macOS versions
   in the tag are **ignored**, so the wheel tags decide the real minimum OS.
   The Python tag must be this exact `cpXY`, `cpXY-abi3` with XY no newer than
   ours, or `py3`.
2. Before that, derives the zip's `python_versions` from the wheel tags
   (`abi3` and `py3` count as any 3.x) and refuses the extension on another
   Python.
3. De-duplicates across **all** enabled extensions by distribution name,
   keeping the highest version (then the file name), and installs the result
   into one shared `extensions/.local/lib/pythonX.Y/site-packages`. If another
   extension bundles a newer pyproj, GeoTools runs with that one. The About
   panel shows the version that actually loaded.

Since step 3 ignores the Python tag, a zip must never hold two wheels of one
pin for the same platform. `build_extension.py` refuses that.

## Building

```sh
python scripts/build_extension.py --blender /path/to/blender
```

The script:

1. copies `geotools/` to `.build/staging/geotools`;
2. adds `platforms` and `wheels` to the staged manifest from the wheels in
   `geotools/wheels/`, after checking that every pin has exactly one wheel for
   each platform it builds;
3. runs `blender --command extension validate`;
4. runs `blender --command extension build --split-platforms`;
5. validates each zip.

It writes one zip per platform to `dist/`, named
`geotools-<version>-<platform>.zip`, for example
`geotools-0.3.0-dev-linux_x64.zip`. If only some platforms have wheels, it
builds only those and says so. Use `--out DIR` to write elsewhere. Use
`--no-wheels` for a single zip without the bundled libraries, and `--python X.Y`
for a local Blender that is not on CPython 3.13 (see above). The repository
manifest is never changed.

A platform zip carries about 10 MB of pyproj on Linux, 6.7 MB on Windows
and 5.0 MB on macOS arm64, on top of rusty-tiles.

`--blender` defaults to `blender` on `PATH`.

## Running the tests

Core tests, from the repository root:

```sh
python -m pytest
```

`pyproject.toml` points pytest at `tests/core`.

Blender tests run inside Blender against the installed extension. One command
builds the zip, installs it into a temporary profile, runs `tests/blender/` and
cleans up:

```sh
# Without rusty-tiles and pyproj bundled (builds with --no-wheels)
python scripts/run_blender_tests.py --expect missing

# With the fetched wheels bundled; checks the pinned versions load
python scripts/run_blender_tests.py --expect available
```

With `--expect available` it asks the Blender for its Python version and builds
for it, so on a Blender running 3.14 fetch the wheels with `--python 3.14`
first.

Use `--blender PATH` (or `$BLENDER`) to pick a Blender, `-k NAME` to run some
tests, and `--keep` to keep the temporary profile for debugging.

The preview tests (core and Blender) need a rusty-tiles CLI and a Cesium 1.146
`Build/Cesium` folder, which are not bundled. Point
`GEOTOOLS_TEST_RUSTY_TILES_CLI` and `GEOTOOLS_TEST_CESIUM` at them to run those
tests; without them they are skipped. Blender's
Python has no pytest, so `tests/blender/run_suite.py` is a small runner of its
own.

CI (`.github/workflows/ci.yml`) runs on pull requests and on pushes to `main`
and `develop`. It has these jobs:

- `core`: ruff and pytest, with pyproj installed at the pin so the reprojection
  tests run.
- `blender`: an official, checksum-pinned Blender 5.2 LTS runs the Blender
  tests with `--expect missing`, then uploads the zip.
- `blender-wheel`: the same with the pinned PyPI wheels (rusty-tiles 0.4.1,
  pyproj, certifi) and `--expect available`, so the publish, inspect and CRS
  tests run against the real wheel. A failure fails the run; it never falls
  back to a wheel-less build.
- `core (pytest, macOS arm64)` and `core (pytest, Windows x64)`: the core
  tests (no ruff) on `macos-latest` and `windows-latest`, at the same pins.
- `blender (macOS arm64, no wheels)` and `blender (Windows x64, no wheels)`:
  the `blender` job on the official macOS `.dmg` and Windows `.zip` of the same
  Blender, each checksum-pinned (`BLENDER_SHA256_MACOS_ARM64`,
  `BLENDER_SHA256_WINDOWS_X64`) and cached.

The macOS and Windows jobs are not required checks yet; a failure there still
needs fixing before a release, since every platform zip ships.

`.github/actions/setup-blender` downloads, verifies and caches the Blender
build for its `platform` input (`linux-x64`, `macos-arm64` or `windows-x64`).
When you update the pinned Blender in `ci.yml`, take all three checksums from
the release's `.sha256` file, and update `release.yml` to match.

## Screenshots of the sidebar

Panel tests draw into a stub layout, so they cannot show truncated labels or a
cluttered panel. For UI work, look at the real thing:

```sh
python3 scripts/ui_screenshots.py --out /tmp/geotools-shots
```

It builds and installs the extension into a temporary profile, opens Blender
on your screen for about 20 seconds, builds a demo scene (a terrain with a
face, a category and a texture layer, a build profile with a variant and a
`.glb` profile, checks run and one publish when rusty-tiles is bundled) and
writes PNGs of the GeoTools sidebar: `montage.png`, `montage_texture.png` and
`montage_glb.png` (the `.glb` profile, exported once) with every panel open,
scrolled top to bottom, and `state_empty.png`, `state_mid.png` and
`state_ready.png` with the default open and closed panels. `--states` picks
some of them. On Linux it runs Blender on Xwayland (`WAYLAND_DISPLAY=`) unless
you pass `--native`; it needs a display, so it does not run in CI.

## Docs site

The site at <https://bendyson-arch.github.io/blender_geotools/> is built with
[MkDocs](https://www.mkdocs.org/) and
[Material for MkDocs](https://squidfunk.github.io/mkdocs-material/) from
`docs/`, the root `CONTRIBUTING.md`, `CHANGELOG.md` and `LICENSE`.
`mkdocs.yml` holds the nav; `requirements-docs.txt` pins every package. To
preview it with live reload at <http://127.0.0.1:8000/>, from the repository
root:

```sh
uvx --with-requirements requirements-docs.txt mkdocs serve
```

or, without uv:

```sh
python3 -m venv .venv-docs
.venv-docs/bin/pip install -r requirements-docs.txt
.venv-docs/bin/mkdocs serve
```

Before you push, run `mkdocs build --strict` the same way (with `uvx` or from
the venv). It must finish with no warnings: CI (`.github/workflows/docs.yml`)
runs it on every pull request, and fails on a broken link or anchor, or on a
page under `docs/` that is not in the `nav` of `mkdocs.yml`. A new page goes in
the `nav`, or under `not_in_nav` with a comment saying why.

Write links as you would for GitHub, relative to the file (`../guide/layers.md#limits`).
`docs/hooks/site_links.py` turns links that leave `docs/` into site pages
(`CONTRIBUTING.md`, `CHANGELOG.md`, `LICENSE`) or GitHub links when it builds
the site, and fails the strict build if such a link's target is not in the
repository; the files are not changed. `docs/guide/README.md` is the guide's
landing page on both. Pushes to `main` deploy the site to GitHub Pages; other
branches only build it.

## Isolating the Blender profile

Installing the extension by hand changes your Blender profile. To keep your own
profile clean, point `BLENDER_USER_RESOURCES` at a scratch directory. Blender
then keeps its config and extensions there.

```sh
export BLENDER_USER_RESOURCES="$(mktemp -d)"
blender --command extension install-file -r user_default -e dist/geotools-0.3.0-dev-linux_x64.zip
blender
```

`-e` enables the extension after installing it. Delete the directory when you
are done.

## Branches and pull requests

- `main` holds released code only. It moves when a release is merged.
- `develop` is where work lands. Branch from it and open pull requests against
  it (`gh pr create --base develop`).
- `release/X.Y.Z` is cut from `develop` when a release's scope is complete, so
  `develop` can move on to the next version while the release waits (for
  example on a rusty-tiles release). Work for the release still lands on
  `develop` first. Whenever work in the release's scope lands, bring it over
  with a pull request that merges `develop` into the release branch (a plain
  merge, no cherry-picks), and once more before the tag. In that pull request,
  set `blender_manifest.toml` back to the release's `X.Y.Z-dev` version and
  move the new CHANGELOG entries from `[Unreleased]` into the release's
  section. A fix that only the release needs goes straight to the release
  branch; merge the release branch back into `develop` afterwards and after
  the release.
- `legacy-0.2` keeps the 0.2 importer add-on. It is not developed.

`main`, `develop` and `release/*` are protected by rulesets: no deletion or force
push, changes only through a pull request with review threads resolved, merge
or squash only, and the `core (pytest, ruff)` and
`blender (official 5.2 LTS, no wheels)` checks must pass. On `main` the branch
must also be up to date with its base, and a code-owner review is required
(repository admins can bypass it). Release tags `v*` cannot be deleted or
moved.

## Releasing

Releases are cut from `main` by pushing a tag. `.github/workflows/release.yml`
does the rest.

1. When the release's scope is complete, cut `release/X.Y.Z` from `develop`.
   On `develop`, move the changelog's `## [Unreleased]` entries under
   `## [X.Y.Z] - Unreleased` (with a new empty `## [Unreleased]` above) before
   cutting, then set `develop` to the next `-dev` version.
2. On a branch from `release/X.Y.Z`, set `version` in
   `geotools/blender_manifest.toml`, for example from `0.3.0-dev` to `0.3.0`
   (a suffix such as `0.3.0-rc.1` makes a prerelease), and replace
   `Unreleased` in the `## [0.3.0]` heading with the date. That section must
   not be empty. The release notes are `.github/release-notes/0.3.0.md` when it
   exists (a prerelease uses its base version's page), with `{version}`
   filled in and a link to the changelog; otherwise they are the changelog
   section. `python scripts/release_notes.py 0.3.0` prints them, and fails if
   the page links to a file at the tag that the branch does not have, so a
   page must reach `release/X.Y.Z` together with the guide pages it links to.
3. Merge that into `release/X.Y.Z`, then open a pull request from
   `release/X.Y.Z` to `main` and merge it. The push to `main` deploys the docs
   site; for 0.3.0, enable Pages first (Settings > Pages > Source: GitHub
   Actions) and check that the `docs (deploy to GitHub Pages)` job passes.
4. Tag the merge commit on `main` and push the tag:
   `git tag -a v0.3.0 -m "GeoTools 0.3.0" && git push origin v0.3.0`.
5. The release workflow checks that the tag matches the manifest, is on
   `main` and has a changelog section. It then fetches the pinned wheels for
   every platform from PyPI (for CPython 3.13), builds the three split zips,
   checks each holds a rusty-tiles, pyproj and certifi wheel, tests the Linux zip in
   official Blender, and publishes a GitHub release with the zips, the demo
   data (`examples/drape-contexts/` as `geotools-demo-data-<version>.zip`) and
   `SHA256SUMS` of all of them. A plain version becomes the latest release; a
   suffixed one is a prerelease.
6. Merge `main` back into `develop` (a pull request), and delete the release
   branch.

If the workflow fails after creating the draft release, fix the cause and
re-run the failed jobs: it reuses the draft. A version that was published needs
a new version number, since release tags cannot be moved.

## Bumping a pin

1. Change the version under `[tool.geotools.wheels]` in `pyproject.toml`. For
   pyproj, check that the new version has a `cp313` wheel for every platform
   in `platforms` (on PyPI, "Download files"), and look at its macOS tags:
   Blender does not check them (see "How Blender picks wheels"). For a native
   pin, also check `PIP_PLATFORM_TAGS` in `scripts/fetch_wheels.py`.
2. Run `python scripts/fetch_wheels.py` again. `build_extension.py` refuses to
   build with wheels that do not match the pins.
3. Build, install, and check that the About panel reports the new version.
4. Add a line to the changelog.

If a new Blender release changes its Python version, also update
`BLENDER_PYTHON` in `scripts/fetch_wheels.py`, and `PYTHON_VERSION` in the
workflows.
